# SOP：划词与发音故障的定位、修复和交付

## 目标与验收

目标是用户在真实阅读 app 中完成「选中英文 → 查词图标出现 → 结果对应当前词 → 点 US/UK 听读音」。先确认这条路径，再区分具体故障发生在哪一层。

## 第一步：确认对象与现状

1. 用截图识别实际应用。本次是 Easydict 浮动词典，不是网页自身的朗读控件。
2. 确认正在运行的路径、版本、架构、是否有旧补丁及备份。
3. 检查已有源码和本地变更，保存本次修改前的源码快照与完整 app 备份。
4. 使用精确应用路径，避免多个相同 bundle ID 的备份造成识别歧义。

本次从已有的自定义 2.23.0 开始，没有把别人的未提交变更重置掉。

## 第二步：按症状分层

| 层次 | 要回答的问题 | 有效证据 |
| --- | --- | --- |
| 鼠标选择 | app 是否接收到真实选词 | 选择工作流日志、用户操作 |
| macOS 权限 | 当前签名这份 app 是否被允许读取选区 | 运行时错误与实际选区读取；开关本身不充分 |
| 图标/窗口 | 图标是否出现、是否激活一次 | 用户看到图标、窗口日志的 actionType |
| 按钮调用 | US/UK 点击是否进入播放器 | 真实按钮调用链、播放日志 |
| 音频资源 | 对应 URL 或缓存是否有效 | 请求结果、系统音频文件信息 |
| 最终输出 | 用户是否实际听到 | 用户设备试听 |

不要从“没声音”直接推断“系统音量问题”。也不要因为 URL 可下载，就宣称按钮路径已经修复。

## 第三步：定位代码根因

本次从 `EZWordResultView` 追踪到 `playWordPhonetic`，再到补丁包裹的播放入口。确认带 URL 的第一次点击会被当成过期回调拦截，而不是按钮没有连到事件处理。

最小修复：在真实 phonetic 入口的同步调用范围内标记新请求，用 `@finally` 清理标记。保留异步取消路径，不以“全部 URL 一律放行”代替正确区分。

## 第四步：先验证源码与副本，再部署

1. 对 task-only diff 做代码审查；不要把原有功能算成本次新增，也不要把编译通过当作审查通过。
2. 用 clang 编译 arm64 / x86_64 补丁；检查 load commands 和有效签名。
3. 为部署脚本检查失败路径：版本不匹配、空间不足、无法退出、签名失败都不能留下半安装 app。
4. 备份精确的当前应用，保留还原路径。
5. 在临时 app 副本上完成注入和签名。成功后再替换真实应用。

本次最初实机修复采用已存在的注入补丁结构；分享套件另外增加了更严格的注入检查与可回退部署器。完整 app 的 Xcode build/test 没有在本机运行，因为机器只有 Command Line Tools。

## 第五步：重新建立正确的系统授权

重新签名后，旧授权可能与新代码签名不匹配。本次真实发生过 UI 开关 on、读取选区却持续 `AXError.APIDisabled` 的情况。

用户操作：删除旧 Easydict 权限行 → 加入当前精确路径 → 开启 → 自行完成系统验证 → 重启 Easydict。不要直接编辑 TCC 数据库，也不要靠关闭安全保护解决。

开发者在有现成读取权限的环境中曾通过只读比较系统审批条件与 `codesign` requirement 证实根因；这只是本次取证方法，不是普通用户部署的前置条件，不应为此索取 Full Disk Access。

## 第六步：真实行为验收

先在简单页面选词，再在用户最常使用的软件里重复。分别点 US、UK，并在播放结束后重复点击；换词检查是否播放新内容。

本次证据链是：用户确认按钮出现；在聊天 app 中实际选中 `stale`，日志产生 `auto_select_query`，打开结果；自动朗读和 US/UK 按钮进入原生本地音频播放。用户随后明确反馈修改后的 app 可用。

自动化工具若不能控制某个应用，使用用户真实操作与相应日志进行验证，不绕过工具的访问限制，也不把其他软件中的测试说成该软件已经通过。

## 第七步：分享与维护

只发布可审查源码、部署/回退工具、许可证、验证范围和用户文档。将本机日志、系统授权数据库、截图中的个人内容、账号偏好、API key 留在本机。

每次更新都记录支持版本、变化、实际验证和限制。下一次复现仍从用户真实症状开始，避免只重复上次“开关已经开了”的结论。
